# 图的持久化与查询：存储层设计

日期：2026-10-23。状态：**设计决定与实施约束**，不是数据库迁移已完成的声明。
原图/逐body检查点已恢复为分片inventory并完成实际验收；SQLite图索引已实现，
同一真实归档的首次构建与局部查询验收PASS，不代表全模型覆盖通过。
本变更解决第一阶段模型产物无法发布的问题，不开始优化阶段。

## 1. 问题与选择

真实源码恢复已产生1627个body检查点、840个原图，未压缩合计513,803,391字节。
最终单个inventory JSON在256MB独立写入上限处失败；原检查点完整保留。调大上限
只能临时容纳当前产物，不能解决局部加载、增量更新、关联查询及并发访问。

应分开三个问题：规范模型是什么、如何查询模型、如何保存和交换原始证据。
操作/值/状态/区域/资源的类型不由文件或数据库表决定，存储格式也不是化简规则。

| 方式 | 适合承担的职责 | 本项目当前选择 |
| --- | --- | --- |
| 单一嵌套JSON | 小摘要、交换和人工检查 | 不作为大模型主存储；保留旧格式兼容 |
| 分块JSONL/压缩artifact | 原始事件流、不可变源码/图快照、归档与重放 | 继续使用；按有限大小及准确边界分块，独立hash/版本 |
| SQLite索引及类型化关系表 | 本机实体定位、入边/出边、区域展开、跨片连接、快照与事务 | 首个实际查询索引，使用现有Python sqlite3；源码归档首次建库/局部查询PASS，成本见第7节 |
| 服务型图数据库 | 后续可能的大规模图遍历/多人远程并发服务 | 当前无此部署需求；未来按实际查询与并发瓶颈评估 |
| 列式事件存储 | 后续可能的海量时间/性能批量聚合 | 暂无必要替换已保留原档；不承担可变状态/控制语义 |

数据库本身仍持久化为文件。重要区别是能否按索引定位局部记录、保持一致事务，
以及是否必须整体解析。SQLite官方说明其可用于应用数据格式和局部提取，支持
recursive CTE遍历树和图：
[用途](https://www.sqlite.org/whentouse.html)、
[递归图查询](https://www.sqlite.org/lang_with.html)。
本机lewm环境实查sqlite3所链接SQLite为3.53.4；这是可用性事实，不是吞吐结论。

## 2. 两类保存职责与一个模型来源

```text
ModelStore（统一查询接口）
  ├─ 类型化实体、关系及索引
  │    snapshot / namespace / region / entity / relation / evidence reference
  └─ 不可变artifact引用
       原source / provider原档 / 分片规范IR / capture与重放收据
```

第一版SQLite先作为从原规范记录可重建的索引：每条索引绑定artifact SHA、精确
record locator、namespace和schema。规范producer/use/state等事实仍取原记录，
不得在数据库和分片文件里分别维护两套能独立修改的事实。后续若迁移规范记录的
存储权威到数据库，需要显式schema迁移和往返一致性验收，不能静默切换。

不要将整个ProgramGraph作为一条巨大JSON塞进数据库。应按类型化记录和真实
关系查询，必要时加载相应Region的原规范片段；长trace和源码内容通过artifact
locator取回。摘要、显示边和缓存可派生，必须能指出原始依据并重建。

## 3. 身份与分片

分片不是按照源码目录截断程序，也不意味着子图彼此独立。

- 规范定义优先按版本化Region/body及所属表示归档；source module保存来源索引。
- 动态记录按Run/Process/Thread、序列范围与大小分块；跨块调用/事件保持原身份。
- Value、共享StateLocation、Allocation和Resource按其真实身份引用，不在每片复制
  一个同名对象。视图、物化和同逻辑版本的副本关系不能因跨文件丢失。
- 现有ID未必跨body文档唯一。查询键必须包含artifact/表示/body命名空间、实体
  类型及原local ID；路径、文件序号、行号均不能单独充当全局身份。
- 分片之间保存有序端口、实际调用、结果、状态、alias、控制/异常、生命周期及
  异步顺序关系。未知边界仍是OPEN，不能因切片而消失。
- 一个逻辑Region过大时可以物理分块，但不改变原Region及其控制/状态语义。

## 4. 查询与并行

最少需要实体定位、Region展开、producer/ordered consumers、入边/出边、调用
及返回、状态读写、alias/物化、资源使用与生命周期、来源及覆盖义务查询。
不同关系使用明确类型及索引；不能把所有关系都当成普通数据依赖。

并行单元是带输入/输出/状态/资源边界的子图任务，不是磁盘文件。各worker读取
同一不可变快照，生成带基础快照和依赖集的结果；由协调者检查共享依赖及冲突，
统一发布新快照。第一阶段只并行恢复/查询，不生成优化计划。

SQLite WAL允许读写并行，但同一数据库同时只有一个writer，且WAL不适用于网络
文件系统。[官方并发约束](https://www.sqlite.org/wal.html)。因此后续实现须先查明
数据库所在文件系统：本地盘可采用单writer批量事务+多个只读worker；网络盘上
不能直接启用WAL冒充同等并发。单文件不是并行分析的障碍，锁与事务模式才是
需要实测的约束。未来跨主机多writer不在当前范围。

## 5. 增量与发布

模型发布绑定不可变SnapshotID；BUILDING与已验证PUBLISHED分开。先保存并校验
artifact/片段，再发布根manifest或提交根快照事务。中断、预算失败或未闭合模型
可以留有检查点，但不得被读者误当完整模型。完整性状态与存储发布成功分开。

重建以源码/编译/环境版本及实际输入证据决定失效范围。分片hash只证明原字节，
不能证明跨运行的值不变。索引改变不修改原证据；旧快照可复核，新快照显式记录
新增/失效事实和依据。跨库事务不靠分文件自然获得原子性。

## 6. 当前最短落实顺序

1. 用已保存检查点恢复原inventory的分片归档；manifest只索引原source/body与
   全局组件，不再先构造巨大嵌套JSON。复用原图校验，保留原失败及未尝试分母。
2. 让组合/调用适配器按需读取分片；旧JSON公共读入和重放语义保持原定义。
3. 为上述真实产物建立SQLite实体/关系定位索引，复用规范ID与原artifact locator；
   验收局部查询、跨片关系、引用完整性及恢复，实测后报告成本。
4. 完成实际调用、逻辑来源、状态与物理资源连接，按第一阶段合同验收。

选择存储不应变成新的长期基础设施项目。不会因引入数据库就宣称图连接已完整，
也不会因图可查询就宣称后续的reuse/hoist/delete合法。

## 7. 当前实现与真实验收

- 源码归档：151 source shards、13 global components，通过真实1627检查点恢复；
  840原图、787 UNSUPPORTED、590 NOT_ATTEMPTED全部保留。新manifest为63,577字节，
  新增分片约7.8MiB，原图检查点通过locator引用而不复制。
- 查询层：`scar/store/graph_index.py` 使用明确实体/关系表及原artifact locator。
  实际首次构建PASS：437,228实体、1,172,205关系、289,298facts；151/2217/1627/840
  分母守恒，SQLite integrity=ok、FK0，包含/producer+重复Use/StateAccess原locator
  查询PASS。构建418.65s、含验收426.82s、peakRSS192,992KiB，DB481,460,224bytes。
  仍有42,767条显式保留但未语义索引的endpoint引用，不能声称全部关系已经索引。
  本地保留DB，Git保存脚本/固定manifest/DB SHA/查询收据，不提交大型派生库。
- 动态IR归档：`scar/store/bundle_partitions.py` 直接遍历现有记录，不调用完整
  bundle.to_dict；已有真实CPU原档导入的全部25表786条记录、顺序和chunk收据逐条一致。
  同一方式对新的完整LeWM物理采集联合导入及独立实档审核已PASS：2,259,781原记录/
  195chunks；完整模型仍OPEN。成本、校验范围和剩余断口见该实验README。
- 旧protocol snapshots与旧JSON入口保持兼容；不能宣称所有输出已迁移。

实现接口与边界分别见 [GRAPH_INDEX.md](GRAPH_INDEX.md)、
[BUNDLE_PARTITIONS.md](BUNDLE_PARTITIONS.md)。SQLite只是可重建索引；版本化规范
记录及原始证据仍是事实来源，没有数据库与文件各自独立可写的双重权威。
