# 程序类型与依赖图

日期：2026-10-13。状态：**类型设计及 N1 有限核心已实现；自动源码构图仍待 N2。**
N1 范围和证据见 [N1_ACCEPTANCE.md](N1_ACCEPTANCE.md)。

本文件明确 SCAR 首先需要的类型体系。这里分析的是程序的值、操作、状态、
控制和资源关系，不要求理解视频内容、图像场景或模型的业务目的。
旧文档中的 Semantic Graph 在这个范围内应理解为程序类型与依赖图。

## 1. 图中的实体类型

| 类型 | 表示什么 | 示例 |
| --- | --- | --- |
| Value：值 | 某个定义产生的值或区域参数 | 数字、数组数据、引用、一个状态版本 |
| StateLocation：状态位置 | 可以被读取、修改的位置或状态域 | 数组内容、字典项、对象字段、文件内容、RNG 状态 |
| Operation：操作 | 在指定输入、状态和控制条件下发生的操作 | 加法、读取、写入、复制、调用、等待 |
| Region：区域 | 可递归展开、带明确边界的操作子图 | 函数体、循环、分支、整个处理阶段 |

这是目前选择的**结构类型**。它们不是完整的操作类型清单，也不要求每行代码
只能归入其中一类。一行 `a[i] += f(x)` 会展开成读取、调用、计算和写入等操作，
连接其值和状态位置。

Value 的强类型变体及位置、身份规则沿用 [CORE_GRAPH_MODEL.md](CORE_GRAPH_MODEL.md)。
Resource、Materialization 和执行事件在实现/证据图中另有类型；不能说 SCAR
所有图中的节点总共只有四种。

输入、输出是值在区域边界的角色；常量和循环不变量是带范围的性质；shape、
dtype 是数据类型/表示属性。一个输入可以同时是某循环的不变量，又是上层操作
的输出，因此它们不能成为互斥的数据节点类别。

## 2. 操作的基础行为类型

下面是组合式分类，不是互斥枚举。一条复合操作可以具有多种行为，展开后由
内部子图说明每种行为发生的位置。类型用于选择分析规则，具体算子、输入及
状态依赖仍需保留。

| 行为类型 | 定义 | 常见实例 | 既有标签对应 |
| --- | --- | --- | --- |
| 计算/生成值 | 从输入产生新的结果 | 加法、索引计算、归约、解析、压缩、编码 | VAL |
| 读取状态 | 从指定位置和版本取得值 | 读取数组、对象字段、配置、文件内容 | STATE/read |
| 写入状态 | 修改指定位置和范围 | 原位赋值、容器更新、文件写入、RNG 更新 | STATE/write |
| 建立或改变表示 | 改变布局、类型或访问视图 | reshape、view、cast、序列化 | REP |
| 管理生命周期 | 分配、保留、复用或释放资源 | allocate、retain、reuse、free | MEM |
| 搬运/物化 | 在物理位置或表示实例之间传递数据 | CPU/GPU copy、buffer copy | XFER |
| 控制执行 | 决定执行对象、路径、次数或退出方式 | call、dispatch、branch、loop、return、raise/handle、enqueue | CTRL |
| 建立顺序/等待 | 约束发生先后或等待完成 | wait、synchronize、barrier | ORDER |

IO 表示访问外部位置/交互边界，例如文件、socket、环境接口；不根据载荷是
视频、tensor、文本再发明一套基础类型。既有 IO 标签可保留，用作边界属性。
同样，随机采样是读取/推进 RNG 状态并计算新值的组合；import 是解析、加载、
执行初始化和更新模块绑定等操作的组合。

引用、alias、escape 与身份是值/位置之间的关系及操作接口效果。它们必须
明确保留，不能因已贴 REP 或 MEM 标签就推定具体关系。

REP 下的 view、cast、编码等仍有不同的具体操作规则；不能由“改变表示”推出
值相等或共享存储。生命周期关系还须包含 ownership、retain 和存活范围；
释放一个引用不等于立即释放共享存储。Order 的端口区分主机返回、设备就绪
和等待完成，不能只留下泛化的“同步”标签。

读取还需要位置的稳定性与外部写入范围：时钟、文件或共享内存可能在图外
变化，不能因图内没有 Write 就证明值恒定。未知稳定性应作为具体分析缺口。

OPAQUE/UNKNOWN 描述分析的已知程度，不是程序天然的一种业务行为。未解析
的调用仍是调用，但其读写、目标或效果可能尚未确定；缺口应分项报告。

上述表细化既有标签。N1 在新核心中实现对应 Behavior 类型，旧 collector 和
backend 保留；行为分类本身不提供具体算子的计算/效果证明。

## 3. 视频保存与 tensor 保存的统一表示

两者可使用同一个保存区域接口：

```text
数据值 x + 编码参数
        │
        ▼
编码/序列化子图 ──► 字节值 b
                         │
目标位置 + 写入模式 + 旧状态 ──► 写入 ──► 新状态 + 完成出口
```

这不是要求所有库都先生成一个完整字节 buffer：分块或流式写入时，将内部
展开成循环、分块值、编码器状态和多次写入。写入目标、模式、偏移、可见范围
与完成条件由同一套状态/控制接口表达。

不需要 VideoSaveNode 和 TensorSaveNode，也不需要理解载荷在人类层面的意义。
具体编码实现仍在操作/子图中，不能因为都是“计算”而视为相同函数。

共同的图化简规则可以判断：编码输入及相关状态不变时是否可共享编码结果；
字节值是否被重复搬运；某次写入是否在任何要求保留的观察之前被完整覆盖。
这些判断依据值、状态、消费者、控制和效果依赖，不依据文件扩展名或变量名。
外部写入既不因是“视频”而天然不可优化，也不因内容相同就自动可删除。

## 4. 连接类型

图至少区分以下关系，完整端口约束见 CORE_GRAPH_MODEL：

- **值的定义与使用**：谁产生，哪个准确的输入位置使用。
- **状态读取与更新**：访问哪个位置、范围和前后版本。
- **引用与共享**：哪些值访问同一位置，是否部分重叠。
- **控制**：哪些条件、循环和出口决定操作发生。
- **顺序与完成**：哪些操作必须先完成，哪些值尚未物化就绪。
- **区域包含与接口绑定**：如何展开子图以及跨层传递参数和结果。
- **物理实现对应**：逻辑值对应哪些 storage/materialization/设备及运行事件。

状态读取/更新等是查询层关系，底层通过精确 use、状态版本与位置端口组合
表达；不能与规范字段各维护一份互不一致的事实。

类型使分析知道应使用哪类规则；依赖图决定具体操作能否删除、共享、上移或
延迟。例如“读取”类型本身不能证明两次读取之间没有写入，而状态版本关系
可以支持或否定该判断。

## 5. 如何构图与验收

从源码恢复可判定的定义、使用、绑定、控制与读写；解析函数时按其内部操作
递归展开，或接入已核对的基础算子接口。实际 dispatch 和库边界证据不足时
保留明确缺口。不能用函数名称、业务标签或人工 pure=True 替代关系恢复。

N1 继续按既定范围实现结构和接口；N2 接前端；N3 检查依赖与化简指导。
增加一条类型体系验收要求：两个业务名称不同但基础操作与依赖结构相同的
通用 testcase，应进入同一套分析规则。通过这种测试不代表完整视频编码库
或 torch.save 实现已被自动解析。

后续判断类型是否足够，要看完整程序能否连接并支持这些查询。可以细化或
修订类型；不通过不断添加业务类别弥补读写、控制或依赖关系缺失。
