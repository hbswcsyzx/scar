## Observations

- On a Created generator, NEXT and SEND(None) enter the body and suspend at its first yield. SEND(non-None) raises TypeError without entering the body and leaves the generator Created; a later NEXT can start it. An invalid THROW arity likewise raises TypeError before entering the body and leaves it Created. CLOSE on Created closes without a body entry.
- A valid Created THROW instance or exception class enters no user-body code and closes the generator. Throwing a StopIteration instance at this point raises that original StopIteration with no cause and closes the generator. A class whose exception constructor callback raises RuntimeError also leaves the Created generator closed, with the callback log set and no body entry.
- On a Suspended generator, NEXT/SEND resume the body; SEND values are visible at the suspended yield. THROW can be caught by the body and yield again. The same raising exception constructor, when thrown at this Suspended generator, produces a RuntimeError that this witness body catches, then yields; the generator remains Suspended. Thus the Created and Suspended constructor-failure paths have different body-entry and lifecycle outcomes.
- A generator body that is actually reentered reports `GEN_RUNNING`. NEXT, SEND, valid THROW, and CLOSE attempted from that body raise `ValueError("generator already executing")`; the active body remains running and continues to its next suspension. Invalid THROW arity raises TypeError before the reentry check. For a nested THROW using the raising exception class, its constructor callback did run and log, but its RuntimeError did not escape; the operation reported the reentry ValueError. After the outer drive returns, the generator is Suspended and can be driven again.
- A Suspended close caught by the body and followed by `return "generator-return-during-close"` makes `close()` return that value on this CPython version and leaves the generator Closed. A close cleanup that raises RuntimeError propagates that error and closes the generator.
- If close is ignored by yielding, `close()` raises `RuntimeError("generator ignored GeneratorExit")` and leaves the generator Suspended. The same occurs when a `finally` block yields during close. Retrying close then closes the generator; a later NEXT raises StopIteration. The `finally` body after its yield was not observed to run during the retry.
- When the body catches an externally thrown StopIteration, it can yield again and remain Suspended. When the exception escapes the Suspended body, the caller receives `RuntimeError("generator raised StopIteration")` with the original StopIteration as `__cause__`, and the generator closes. An internal StopIteration raised by the body after resume has the same PEP 479 wrapping and closes. The Created THROW StopIteration case above remains the original exception, not this body-exit conversion.
- The legacy `throw(type, value)` form emitted a DeprecationWarning in the Suspended case on this runtime. Traceback frame lists varied: some failures exposed a generator frame, while the PEP 479 RuntimeError cases exposed only the observer call frame. The captured traceback is therefore not a reliable substitute for an explicit source/route relation.
- Closed generators stayed Closed: NEXT and SEND raise StopIteration, THROW raises the selected exception, and CLOSE returns None. No operation restarted the body.

## Contract connection and limits

The observations fit the distinctions in [`M1_PROTOCOL_CONTRACT.md`](/tmp/scar-structured-model-280qf4mi/docs/M1_PROTOCOL_CONTRACT.md): Created pre-entry rejection is different from a no-user-entry initial throw; body ingress and body outcomes are different from host adapters; Suspended close may produce another suspension before a later close completes; and PEP 479 applies to an escaping body StopIteration, not indiscriminately to every StopIteration request.

The static clauses provide places to declare these routes, but this witness does not establish profile applicability or that a supplied protocol inventory is complete. Runtime truth depends on the actual request, object state, selected N/R branch, callback behavior, and body/host route. A Created invalid request must retain the Created state and must not seed body-finished facts. A valid Created THROW or constructor failure can close without body ingress and needs its own selected transition/host route. A failed close that yielded must retain a suspended body for a later drive. The Running reentry error is not a body terminal; the containing body can continue. In each case, only the actual captured CFG/result/state ports can establish the static connection; exception names or terminal kinds alone cannot.

The existing six-case evidence at `model_protocol_families/created_throw_witness.json` independently records Created THROW behavior, including invalid raw `42` remaining Created, constructor failure closing, and initial StopIteration propagating unchanged. Its earlier assertion failure is preserved there; this matrix is a new observer, not a repair or rewrite of that evidence.

This is one bounded CPython build and a small hand-authored generator body. It is not a full Python-family matrix, a runtime collector, a SCAR test pass, or native/source equivalence evidence. No pytest, full regression, profiler, GPU, or LeWM workload was run.
