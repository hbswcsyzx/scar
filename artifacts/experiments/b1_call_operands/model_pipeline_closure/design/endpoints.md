# R3.3 endpoint/protocol interface review

**Status: Proposed, read-only design.** Reviewed clean HEAD `bccefcfb65dcdba71c050cbbecadd3b2f30f3fa2` in `/tmp/scar-structured-model-280qf4mi`; no tests or workloads were run. This note covers endpoint/protocol connections only. It does not close R3.3, M0–M2, source recovery, or runtime correspondence.

## Finding

The current model can preserve the identities and original ports needed to describe a file, buffer, device resource, content read/write, work outcome, queue order, observation, and handle lifetime. It cannot yet interpret an endpoint `ProviderFactReference` as a specific read/write/flush/close/persistence operation. In particular, an `EndpointDomain` is intentionally never reported as matched: equality of its target and a `ProtocolFactReference` does not establish the endpoint visibility rule.

The smallest next step is a closed, versioned endpoint-protocol profile resolved through existing `ProviderFactReference` fields, then a query that instantiates its declared roles from the existing ProgramGraph/ExecutionModel ports. Keep actions, state, and producers in the existing core and execution rows. Do not treat a profile reference, successful call return, completed work, queue order, handle end, or `BytePrefixWrite` alone as proof of persistence.

## What the existing records can connect

| --- | --- | --- |

A label or matching static resource ID does not prove a file descriptor refers to a path or that a state write is a byte write. |
| Dynamic resource/handle | `ResourceInstance` + realm/origin → `ResourceRealization` / `RequirementBinding` → `ResourceAccessBinding(operation, requirement, handle, support, constraints)`; `HandleBinding` carries target, start/end, rights, ownership and support | Exact owner/target/handle foreign keys and known contradictions are checked. `ProtocolCondition(rule,condition,uses)` and `ImplicitBinding(rule,support)` are still references/claims; they do not define an operation’s native meaning. `EndedAt` means the declared handle lifetime ended, not data sync or durability. |
| Logical input/materialization | `ValueOccurrence` → `ValueDenotation(DataIdentity(VersionRef))` or object identity; `ContentRead` retains the original `UseRef`/`AccessRef`, effect, anchor/support, `MaterializationRef`, and storage or endpoint target | `StorageContent(RegionRef)` uses exact ValueGraph scope and byte geometry. `EndpointContent` can identify a `ResourceTarget` and select an original `UseRef`, `AccessRef`, `ProtocolSelector`, or `Unresolved`. A selector does not say that the selected value is a file offset, buffer span, or device address. |
| Work and state effects | `WorkSubmission` retains original `AccessRef` / `InvokeBoundaryStateEffect`, queue/direct scheduling, exact materializations, and coverage declarations. `ResourceOutcome` separates `COMPLETED`/`FAILED`/`CANCELLED`, an effect frontier and quiescence. | Work membership, normal/raise state ports and partial effects remain checkable. A completed outcome does not identify whether bytes reached a buffer, kernel, device, or persistent medium. A frontier is the actual canonical effect list, not a semantic interpretation of each effect. |
| Queue/event order and lifetime | `QueuePrefix`, `EventRecord`, `QueueWait`, `OrderAssociation`; `WorkRetention` / `BorrowRelease`, `HandleBinding.end`, `TargetLifetimeEvent` | The model can preserve a generation-specific queue/event/order path and distinguish work quiescence, borrow release, handle end, and target retirement. Queue order is only queue visibility. None implies endpoint flush or persistence. |
| Produced content | `WriteAssociation(stage,writer,production,placement,evidence)`; `OutcomeProduction(outcome,frontier,actual,rule)` or `EstablishedProduction` | Writes can point to original operations/effects, work, ValueGraph materializations, endpoint targets, scoped EEG/raw/native ports, and protocol selectors. Validators keep source joins and physical/native applicability unresolved where the facts do not close them. |
| Required observation | scoped `ObservationRequirement` + `ObservationRoot(actual,interval,anchor,support)`; `ContentRead(ObservationConsumer(root), ...)` | Q preserves an explicit output/endpoint obligation and actual endpoint/value association. Its protocol and interval are not parsed into a read, flush, close, or persistence rule; an absent root/read remains a missing obligation. |

Core access modes are limited to `READ`, `WRITE`, and `READ_WRITE`; footprints are `WHOLE`, `INTERVAL`, or `UNKNOWN` [model.py:107–129, 363–400]. Resource identity is separate from state: `ResourceLocation` maps a `StateLocation` to a static `ResourceDefinition` [program/resources.py:170–179]. This is enough to attach an existing state edge to a declared resource, not to assign units or OS/device semantics to it.

## Exact limits in the current endpoint path

- `ProtocolSelector` is only `{reference: ProviderFactReference}` [content.py:272–278]. A provider reference has an artifact digest/schema and locator, but the generic reference does not parse the locator or establish truth [providers.py:47–71]. The same applies to `ProtocolInterval.protocol`, `ProtocolCondition`, resource rights, queue/order protocols, and Q protocols.
- `resolve_placement` resolves an exact ValueGraph materialization and target. For an endpoint, a `ProtocolSelector` emits `content_selector_protocol_unverified`; a Use/Access selector still needs endpoint/protocol alignment [content_validation.py:312–356]. `EndpointContent` also rejects a known storage-backed materialization region rather than silently relabeling it as an endpoint [content_validation.py:346–355].
- `check_interval` validates known scope and ordering, but explicitly leaves native clock/protocol correspondence unresolved [content_validation.py:45–59]. `NativeWorkRead` may narrow an interval, but the validator says it cannot replace whole-work stability without a parsed correspondence [content_validation.py:452–455].
- `BytePrefixWrite` is a fixed, zero-field profile marker [production.py:224–229]. `resolve_actual_range` parses a closed raw payload with `requested_bytes`/`written_bytes`, and only mechanically compares linear rank-1 `uint8` storage regions with the same allocation and offset [production_ranges.py:15–38, 87–140]. It proves neither that an endpoint received those bytes nor a file/device destination offset. It does not accept endpoint placement as the interpreted range; it leaves `production_profile_placement_unresolved` / `production_actual_unresolved` gaps [production_ranges.py:97–110].
- `WriteAssociation` can declare endpoint placement and `OutcomeProduction.actual` can carry `ProtocolSelector`, but `produced_errors` still adds `production_native_protocol_unverified` [production_validation.py:184–227]. A raw result count plus a source buffer prefix is not a physical endpoint write or content-version proof.
- `EndpointDomain` checks the read’s exact endpoint target, then leaves `validity_endpoint_interpreter_unsupported`; the query forces endpoint visibility unmatched [validity_validation.py:447–463, 560–580]. A Q protocol reference cannot currently turn `flush`, `close`, or `fsync` into visibility.
- Observation validation checks contract/facet membership, scope, target and interval, then keeps `contract_endpoint_protocol_unverified`, `requirement_protocol_unverified`, and source/actual correspondence gaps [observation_validation.py:88–113, 115–189]. The root’s actual target or value is not itself proof of persistent content.

## Minimal R3.3 contract/query design

First attempt the connection without a new `ExecutionModel` table:

1. **Resolve a closed profile, not a locator string.** Let an existing protocol field point to an exact provider artifact and locator. The provider artifact must decode as a finite, versioned endpoint-protocol schema. Unknown schema, missing profile, or unparsed action remains `UNRESOLVED`; there is no fallback based on label, URI, function name, return type, `ResourceOutcomeKind`, or `ProviderFactReference` equality.
2. **Define endpoint layers and identities separately.** A profile may describe a path/file entity, open-file-description/handle, process buffer or allocation, device/queue endpoint, and their declared transfer relation. Each instantiated endpoint must reuse the existing exact `ResourceTarget`, `RequirementBinding`, `HandleBinding`, `AllocationTarget`, `MaterializationRef`, and `RegionRef`. Equal path strings, object IDs from different artifacts, queue names, or pointers must not merge instances. Missing alias/target correspondence remains a gap.
3. **Map protocol roles back to original ports.** For each action, the profile identifies the static operation or native boundary and the relevant original parameter/result roles. Instantiate it from the actual `OperationOccurrence`, `CallActivation`, actual `UseRef`/`AccessRef`, `ResourceAccessBinding`, `InvokeBoundaryStateEffect`, `NativeInputRef`/`NativeOutputRef`, and actual completion edge. Keep `UseID`s distinct when two actual arguments hold the same value. Do not store a second producer/use/state graph or infer a call edge from names/spans.
4. **Describe byte semantics with two coordinates.** The profile must state (a) the selected source-buffer bytes, connected to a scoped ValueGraph region/materialization, and (b) the destination endpoint range/offset. It must define how the actual byte count is obtained from the exact return/completion or bounded raw observation and how short/partial writes behave. `BytePrefixWrite` remains a storage-prefix profile; it cannot stand in for an endpoint destination range. If the destination range is not provided/decodable, retain it as unresolved rather than treating `written_bytes` as a complete file write.
5. **Model independent milestones.** A profile distinguishes at least the milestones it actually supports: buffer drained, endpoint accepted bytes, endpoint data synchronized/persisted, handle closed/released, and external content observed. Each milestone points to its own original dynamic occurrence/result or scoped observation and causal order. A write return is not a flush; buffer flush is not `fsync`; `fsync` is not a directory-entry durability claim; `close` is not a persistence signal. Which milestones are required comes from the exact Q contract/facet and protocol profile, not a global ordering enum.
6. **Return a trace of joins and open gaps.** The composition query should preserve the source `ContentRead`, write/production, work/outcome/frontier, event/wait, retention/handle/lifetime, Q requirement/root and original core ports. Report each exact join and each unresolved phase separately, with statuses such as declared/conditional/unresolved/contradicted. Only a parsed profile plus exact joins can eliminate an interface gap; source/runtime/native correspondence remains a separate claim. Never return unconditional `ready` or `persistent=true` from these records alone.

`ResourceAccessBinding.constraints` is the natural existing place to associate an access with a profile rule and original role Uses (`ProtocolCondition`), while `EndpointContent`, `WriteAssociation`, `ObservationRequirement`, and `ObservationRoot` already carry protocol references at their respective boundaries. The profile can interpret those exact references and derive per-occurrence actions from canonical operations. If a concrete R3.3 fixture shows that these existing links cannot identify an action occurrence without ambiguity, add only the smallest typed association for that missing join; do not add an endpoint-stage graph in advance.

## Finite acceptance matrix

| Case | Expected result |
| --- | --- |
| Exact source bytes `[0,16)` requested, actual source prefix `[0,8)`, same allocation and linear `uint8`; parsed actual write result is 8 | Existing storage byte-prefix mechanics may accept the geometry/count relation conditionally. Endpoint destination bytes and persistence remain unresolved until an endpoint profile maps them. |
| Actual source prefix starts at offset 1, uses another allocation, exceeds the requested region, or reports more bytes than requested | Reject the known geometry/count contradiction. Do not let an unknown endpoint protocol mask it. |
| `EndpointContent` selects a protocol reference that is absent, wrong schema, or an arbitrary locator; two equal protocol refs appear on write and endpoint visibility | Keep protocol/selector/visibility gaps. Equality must not yield endpoint-visible or persistent content. |
| Host/write or queued work is followed by `ResourceOutcome.COMPLETED`, event wait, and queue order, but no endpoint sync/observation rule | Preserve queue/work completion facts; endpoint and durable visibility remain missing. Queue order does not imply host or endpoint visibility. |
| `flush` succeeds but `fsync` is absent; or `close` ends the handle without a flush/sync chain | Handle/work state may be structurally valid, but required persistence remains missing. `EndedAt`, quiescence, or close return cannot fill another milestone. |
| `fsync` precedes the relevant write, the write outcome is `FAILED`/`CANCELLED` with an insufficient partial frontier, or close/retirement occurs before a required access | With interpreted exact action semantics, reject/mark contradicted where the canonical order/frontier proves the conflict; otherwise preserve an explicit unresolved protocol/order gap. Do not convert failure to success. |
| Two `OPEN_FILE_DESCRIPTION` instances share a path string but lack an exact alias/source relation | Keep separate targets and an alias gap; do not union writes or claims. |
| Required Q endpoint/facet exists but its root or content read is missing | Keep the original obligation and report the missing join; no empty-contribution success. |
| Bounded OS witness records partial `pwrite`, buffer flush, `fsync`, and `close` in a tiny temporary file | It can establish the tested OS observations in that process. Without exact source/call/port binding it is not an automatic SCAR recovery or general filesystem guarantee. |

## Review of the minimal endpoint-byte profile proposal

I agree with the proposed no-new-table path for one deliberately bounded endpoint protocol. A fixed, closed endpoint-byte profile reached through the existing `ProtocolFactReference`/`ProtocolSelector` can explain a selector’s offset/length roles and one explicitly named rule such as *read-after-completed-write*. `ExternalSnapshots.payload` already verifies exact supplied bytes against the referenced artifact SHA and size without opening its URI [snapshot.py:51–97]; a small whitelist parser can consume those bytes. This adds interpretation of an existing reference, not a new authority bit or a parallel execution graph.

For this profile to close only the intended mechanical joins:

- Resolve only an exact supported schema/version and locator. Missing bytes or an unknown profile is a gap; malformed bytes, wrong profile family, or a contradicted exact endpoint/port is an issue. `ProtocolFactReference` equality alone is never a match.
- Map each protocol role to original inputs/outputs and state: endpoint target/handle, source buffer selector, destination byte offset, requested length, actual result, and action completion. Prefer the existing `ResourceAccessBinding` plus `ProtocolCondition.uses`, `UseRef`/`AccessRef`, `InvokeBoundaryStateEffect`, `NativeInputRef`/`NativeOutputRef`, and `CallActivation`. If one role cannot be recovered from those exact ports, leave it unresolved rather than adding a second argument/result store.
- Reuse the current `BytePrefixWrite` raw parser and exact `RawRecordRef`/result-locator checks. Extend range resolution for endpoint placements only after the profile identifies destination offset semantics. Return separate source-buffer selection and endpoint-destination range; `RegionRef` continues to mean ValueGraph storage. Keep the existing requested/written count, allocation, offset, and source-region checks where they apply. An endpoint profile must not turn an unknown source buffer or unknown destination offset into a full write.
- Let `CompletedVisibility(EndpointDomain(...), protocol=...)` select the same parsed rule only when the exact read, write, production, materialization/version, endpoint, current-state support, and canonical order chain join. The existing `ContributionSupport` already carries the exact read/write/production and visibility alternative. A supported profile can make the *declared read-after-completed-write relation* mechanically queryable; source/runtime applicability and actual native visibility remain separately conditional. This is not a general `MATCHED` shortcut for endpoint-domain rows.
- Keep `flush`, `close`, and persistence distinct. Their `OperationOccurrence`, call/return route, original Uses, `ResourceAccessBinding`, `StateAccess`, and `HandleBinding.end` can already be retained and ordered. A profile action may identify a particular operation as buffer-flush or handle-close; absent such an interpretation, it remains an opaque ordered action. Neither operation means persistent data. If a use case requires durability, it needs a separately named and supported persistence milestone and its own exact result/order/observation joins; a byte-write/read profile must not claim it.

This is implementable in the existing content, range, and validity query paths without an `ExecutionModel` schema bump: teach the closed profile resolver and those queries one explicit supported profile, preserve all current gaps for other protocol references, and add no record table unless a concrete fixture proves an exact occurrence-to-profile join is absent. It is sufficient for a narrow endpoint-byte/read-after-write case. It does not by itself model or prove general buffer flush, close, device protocols, or durable persistence, and therefore is not complete R3.3 acceptance.

For a future positive OS witness, record a tiny endpoint’s requested range, actual short-write result, later read, optional buffer flush/close/sync calls, and the observed bytes/return outcomes under exact raw artifacts and process/handle generations. That witness can test the selected profile’s claims for the tested OS and process. Without explicit source-to-occurrence/port correspondence it does not demonstrate automatic SCAR recovery; even with that join it does not prove power-loss durability beyond the tested protocol’s stated scope.
