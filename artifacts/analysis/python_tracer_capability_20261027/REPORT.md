# Python-call profiler capability check

**Scope.** Read-only check of the installed lewm environment and PyTorch 2.13.0 profiler interfaces, plus one already-run tiny CPU probe. No LeWM workload, collector edit, tool installation, or further probe was performed for this artifact.

**Observed.** Environment: CPython 3.14.7, Torch 2.13.0+cu132. `torch.profiler.profile(with_stack=False)` in the tiny probe exposed Torch operator events only. With `with_stack=True`, it exposed a Python call tree (`nested → leaf`) along with PyCCall/TorchOp events. The earlier probe's raw stdout was not retained; `probe_result.json` records only these observed facts, and `probe_cpu.py` is a reproducible probe, not a rerun.

The installed public event surface supplies a parent/children tree, event timing, and thread-related IDs (`FunctionEvent.thread` / `_ProfilerEvent.start_tid`). Python frame metadata is limited to filename, line, and function name; PyCall fields expose callsite/caller and optional module/optimizer data. It does not expose the tracer's internal `TraceKey` as a stable SCAR CodeID, bytecode CALL offset, exact argument-to-formal mapping, returned object, or normal-versus-exception outcome. Filename/line/function is insufficient to match SCAR's structural `pycode-v2` identity or distinguish code versions. Thus the profiler is useful as a timing/call-tree sidecar, but the installed public API cannot replace SCAR's canonical invocation and operand records.

**Hook constraint.** PyTorch's C++ `PythonTracerBase` implementation uses `PyEval_SetProfile`. SCAR's `CallEdgeRecorder` installs `sys.setprofile`; on the same thread these consume the same CPython profile-hook slot, so concurrent capture needs explicit chaining/integration and is not a drop-in combination.

**Cost assessment (inference, not a measurement).** SCAR already weakly caches supported CodeType structural keys and only emits a full code descriptor the first time a key is written (`code_snapshot.py`; `CallEdgeRecorder._code`). The remaining per-call Python callback/record/lock/ancestry work is a plausible cost center, but this check did not measure its share of LeWM initialization time. A SCAR-owned native recorder could reduce Python callback construction only if it preserves stable CodeID, invocation/parent, entry/exit/outcome/thread keys and joins those records to `sys.monitoring` operand events. No claim is made that this would improve the current capture until the separate helper timing is available.

**Evidence locations.** Local API declarations: Torch `include/torch/csrc/profiler/orchestration/python_tracer.h` (`CompressedEvent`, `PythonTracerBase`), `include/torch/csrc/profiler/collection.h` (`PyFrameState`, `PyExtraFieldsBase`), `_C/_profiler.pyi` (`_ProfilerEvent`, `_PyFrameState`, `_ExtraFields_PyCall`), and `torch/profiler/profiler.py` (`profile.events`). Local SCAR paths: `scar/trace/call_edges.py` (`_code`, `profile`, hook installation), `scar/trace/code_snapshot.py` (`code_key`, `describe_code`), `scar/trace/call_operands.py` (`sys.monitoring` CALL capture). Version-matched upstream implementation: [profiler_python.cpp](https://github.com/pytorch/pytorch/blob/v2.13.0/torch/csrc/autograd/profiler_python.cpp) and [profiler README](https://github.com/pytorch/pytorch/blob/v2.13.0/torch/csrc/profiler/README.md).

Reproduce the capability probe with `/home/zyf/miniconda3/envs/lewm/bin/python -B probe_cpu.py`. It is deliberately a tiny CPU-only check, not a benchmark.
